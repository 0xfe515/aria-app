# Repository Guidelines

## Project Structure & Module Organization
Aria is a single-module Android app built with Kotlin, Jetpack Compose, and Material 3. Source code lives in `app/src/main/java/com/ariateam/aria/`: `MainActivity.kt` hosts the UI, `speech/` manages speech recognition and wake-word listening, `ui/screen/` contains screens, and `ui/theme/` defines styling. Resources live in `app/src/main/res/`, including audio cues in `raw/`. The manifest declares microphone access.

Local tests belong in `app/src/test/`; device tests belong in `app/src/androidTest/`. Dependencies and plugin versions are centralized in `gradle/libs.versions.toml`.

## Build, Test, and Development Commands
Run commands from the repository root using the Gradle wrapper:

- `./gradlew :app:assembleDebug` — build a debug APK.
- `./gradlew :app:installDebug` — install it on a connected device or emulator; launch Aria from the launcher.
- `./gradlew :app:testDebugUnitTest` — run local JVM tests.
- `./gradlew :app:connectedDebugAndroidTest` — run instrumented tests on a connected device or emulator.
- `./gradlew :app:lintDebug` — run Android Lint.

Configure the Android SDK through Android Studio or `local.properties`. The app compiles against SDK 37 and supports Android API 31 and later.

## Coding Style & Naming Conventions
Follow official Kotlin style (`kotlin.code.style=official`) with four-space indentation. Use PascalCase for classes, files, and composable functions; camelCase for ordinary functions and properties; and UPPER_SNAKE_CASE for constants. Use lowercase underscore names for Android resources. Keep speech lifecycle handling in `speech/` and screen composables in `ui/screen/`. Use Android Studio formatting; no standalone formatter or lint plugin is configured beyond Android Lint.

## Testing Guidelines
Tests use JUnit 4, AndroidJUnit4, Espresso, and Compose UI testing dependencies. Name test classes `*Test` and methods for the behavior they verify. Existing tests are starter examples; no coverage threshold is configured. Add focused regression tests for behavior changes. For speech changes, manually verify microphone permission handling, wake-word recognition, command listening, and cleanup on a device with speech recognition support.

## Commit & Pull Request Guidelines
This checkout is connected to https://github.com/0xfe515/aria-app.git on the main branch. Use concise, imperative commit subjects, such as `Fix speech recognizer cleanup`. PRs should describe the change, link relevant issues, and report validation commands and device details. Screenshots are optional unless the user explicitly requests them; the previous UI screenshot requirement was withdrawn.

## Configuration Hygiene
Keep SDK paths in ignored `local.properties`. Do not commit credentials, signing keys, or generated build output.

## Agent Workflow
This is an isolated development environment. Builds, tests, and lint are part of the agent's work and do not require a separate request. Use the installed Android Studio JDK and Android SDK with the repository's Gradle wrapper. For code or build configuration changes, run `:app:assembleDebug`, `:app:testDebugUnitTest`, and `:app:lintDebug` as appropriate. Run instrumented tests when a compatible device or emulator is available. Fix failures within the task's scope and report the commands, results, and any remaining environment or device limitations. Static review alone does not establish that the app builds or its tests pass. Keep machine-specific SDK paths in ignored `local.properties`.

## Planning and Parallel Implementation (Codex coordinator; Gemini and Copilot workers; quota fallback: GPT-6 Luna)
- **Automatic GPT Account Failover**: The user authorizes automatic switching between their already connected GPT/Codex accounts when an actual provider quota error or account-specific usage status proves the active account's allowance is exhausted. Discover available managed accounts and the system-default account through Orca; select an account with usable allowance using only account/session controls supported by the installed runtime. No repeated user confirmation is needed. Preserve task context, partial changes, exclusive file ownership, model/effort restrictions, and Orca lifecycle authority; settle or fence an implementation attempt before another account edits the same files. Record the exhaustion evidence and effective account switch without exposing credentials or storing account identifiers in this repository. Do not infer exhaustion from silence, timeout, authentication errors, generic rate limits, or aggregate usage for a different model. Do not copy credentials, reset paid credits, purchase usage, or invent unsupported CLI flags. If automatic selection is unavailable, report the specific runtime limitation and preserve work. Account switching does not authorize an otherwise forbidden implementation model or coordinator implementation.
- **Default Supervised Orchestration (Orca)**: For supervised implementation, use the Orca `orchestration` skill (`orca skills get orchestration --json`) and real Orca runtime `Run` / `Task` / `Dispatch` state (`orca orchestration ...`), not a raw `agy.exe` process or a non-Orca subagent as a substitute. Codex (`Codex/gpt-sol`) remains the coordinator; select the implementation worker via `orca orchestration worker-start --spec $taskSpec --worktree current --agent antigravity --model gemini-3.8-flash-high --json`. Plain unsupervised handoff or terminal-only use belongs to `orca-cli` (`orca skills get orca-cli --json`) as the official skill prescribes. Direct headless Antigravity CLI (`%LOCALAPPDATA%\agy\bin\agy.exe`) invocation is retained only as an explicit lower-level diagnostic fallback.
- **Role Split**: Codex (`Codex/gpt-sol`) is responsible for planning, writing precise task specifications, reviewing diffs, performing independent verification, and Git integration. Production source code, tests, build/configuration scripts, and automation code must be authored or modified by Gemini 3.8 Flash High (`gemini-3.8-flash-high`) or an Orca-managed Copilot worker, or by the separate GPT-6 Luna worker only under the quota fallback below. The coordinator must not implement as a fallback. Documentation and task specifications may be authored by the coordinator or delegated under an explicit task specification.
- **Copilot Worker**: Copilot is an authorized implementation and review worker for ordinary work, including parallel tasks; Gemini quota exhaustion is not required. Use `orca orchestration worker-start --spec $taskSpec --worktree current --agent copilot --json` with the enabled Orca agent ID (verify the configured ID before dispatch if it differs). Use the configured Copilot model by default; do not invent a model ID or pass `--model` / `--effort` unless the installed Orca guide explicitly supports those options for Copilot. Verify the requested/effective agent and record the actual model when observable; an unspecified model is not proof of a particular model. Apply the same task, scope, lifecycle, testing, and independent acceptance requirements as Gemini. Do not substitute a direct Copilot CLI or non-Orca subagent for supervised work.
- **Parallel Work by Default**: When a request contains two or more independent implementation areas, create separate Orca Tasks and dispatch multiple eligible workers before waiting. Distribute independent areas between Gemini and Copilot when available; do not bundle unrelated implementations into one worker or serialize them merely because Gemini is the default. Size concurrency to available slots and real dependencies. A single cohesive change, overlapping ownership, or unavailable capacity may require serial execution; record the concrete reason. Supervise every dispatched worker through completion.
- **Parallel Ownership & Shared Resources**: Assign exclusive file paths, peer ownership, shared interface contracts, dependencies, and validation ownership to every Task. Workers must not edit another Task's files. Use Orca-managed child worktrees when edits overlap; verify their baseline because new worktrees do not automatically inherit this checkout's uncommitted/untracked work. Preserve unrelated changes. Route shared-file changes and conflict resolution to an explicit integration Task after prerequisites settle, not competing editors or coordinator implementation. Assign one owner at a time for a connected device, installs, instrumentation, benchmarks, and Gradle/build outputs in a shared checkout. Independently validate the combined result after integration; never benchmark while another worker uses the same device.
- **Model Pinning & Blocker Policy**: Gemini 3.8 Flash High remains the default Gemini worker; Copilot is a separately authorized normal worker: pin `--agent antigravity --model gemini-3.8-flash-high`. Only when an actual provider error or explicit quota status proves Gemini's usable allowance is exhausted may the coordinator use `--agent codex --model gpt-6-luna --effort medium` for implementation. Record and report the quota evidence and model switch in the task specification/result; do not infer exhaustion from silence, a timeout, a generic transient rate limit, authentication failure, missing model, or runtime/CLI failure. Those other blockers require a specific report and stop for the affected attempt; independent authorized Tasks may continue. If Luna is also unavailable, report the blocked Task rather than choosing an unapproved model. Copilot may receive independent work normally or a settled Task under a new explicit specification; fence the prior attempt before transferring ownership. Start new implementation tasks with Gemini again once usable quota is confirmed restored.
- **Quota Fallback Dispatch**: Preserve partial work and settle/fence the Gemini attempt using the orchestration skill's recovery procedure before Luna may edit the same files. For an eligible failed/stopped Task use `worker-start --task <task_id> --retry-of <dispatch_id> --worktree current --agent codex --model gpt-6-luna --effort medium --json`; for work with no prior Dispatch use the full task specification with `--spec`. Never reuse an active or unverifiable attempt as permission to start a competing editor. Luna must follow the same ownership, lifecycle, testing, and independent acceptance requirements. Explicitly requested Luna capability probes are allowed without exhausting Gemini quota; they do not authorize a production switch by themselves.
- **Pre-Dispatch & Task Specification Contract**: Read applicable repository instructions (`AGENTS.md`, [docs/ANTIGRAVITY_DELEGATION.md](docs/ANTIGRAVITY_DELEGATION.md)) before dispatching a task. Every task specification sent to the worker must align with Orca's `Target / Change / Constraints / Ownership / Observable acceptance` structure and explicitly define:
  1. Task ID (`TASK_ID`)
  2. Goal and change (`GOAL` / `CHANGE`)
  3. Current evidence, context, and required reading (`CONTEXT` / `VERIFIED_EVIDENCE` / `READ_FIRST`)
  4. Target workspace, exclusive allowed file paths, peer ownership, shared interfaces, dependencies, and device/build validation owner (`ALLOWED_CHANGES` / `TARGET` / `OWNERSHIP` / `DEPENDENCIES` / `PEERS`)
  5. Forbidden changes and constraints (`FORBIDDEN` / `CONSTRAINTS`)
  6. Behavior requirements including edge cases (`REQUIREMENTS`)
  7. Exact validation commands and verification owner (`VALIDATION_COMMANDS`)
  8. Observable acceptance criteria (`ACCEPTANCE_CRITERIA`)
  9. Required result format (`OUTPUT_FORMAT`)
- **Orca Lifecycle Discipline (Worker & Coordinator)**:
  - **Worker**: Derive the exact executable, flags, terminal handle (`--from` / `--terminal`), `--task-id`, `--dispatch-id`, and heartbeat cadence exclusively from the live Orca-injected preamble (never hardcode a universal heartbeat interval or fabricate/reuse IDs). Send heartbeats at the preamble-specified cadence while actively working (`--type heartbeat --phase <investigating|implementing|reviewing|waiting>`), use `ask` or `escalation` if blocked, run `orca orchestration check --terminal <worker_terminal_id> --json` at natural checkpoints and immediately before `worker_done`, send `worker_done` exactly once with `--outcome succeeded` or `--outcome failed` plus a 3-sentence `--body` summary and true `--files-modified` / `--report-path` values, and remain idle afterward.
  - **Coordinator**: Process every delivered message (`worker_done`, `escalation`, `question`), answer worker questions, verify matching active `taskId` and `dispatchId`, verify outputs, and choose worker reuse, retention, or `worker-release --dispatch <dispatch_id> --json` before acknowledging delivery with `check --ack <delivery_id> --json`. Do not run a manual `task-update` to mark a task completed after `worker_done`. Empty waits (`check --wait`) or unknown liveness do not authorize cancellation, relaunch, or cleanup; follow the orchestration skill recovery receipts.
- **Git & Scope Discipline**: The worker must not run `git commit` or `git push` unless separately and explicitly instructed. Do not alter global `PATH`, CLI global settings, or credentials.
- **Independent Verification & Acceptance**:
  - **Orca Supervised Runs (Default)**: Requested model alone is not proof; Codex verifies `launch.requested` versus `launch.effective` from the Orca launch receipt alongside actual worker evidence, matching `worker_done` (`taskId`, `dispatchId`, `outcome`), `git diff` / `git diff --check`, and independent validation results, and confirms `worker-list --run <run_id> --terminal-state reclaimable --json` after release.
  - **Direct `agy.exe` CLI Runs (Diagnostic Fallback)**: When running the direct headless CLI fallback, a CLI `SUCCESS` status alone is insufficient; Codex must verify that the CLI exit code is `0`, `stream-json` `init.model` is exactly `gemini-3.8-flash-high`, `init.cwd` matches the target workspace, and the final `result` status is `SUCCESS`.
  - In all modes, the coordinator independently inspects diffs (`git diff`, `git diff --check`) and validation evidence, runs validation commands when needed, and dispatches explicit correction tasks to the eligible implementation worker: Gemini or Copilot according to exclusive Task ownership, or pinned `gpt-6-luna` while the documented quota fallback applies. Verify Luna's `launch.requested` and `launch.effective` both name `gpt-6-luna` and effort `medium`; a successful launch or `worker_done` alone does not prove the work passed.
- **Prompting Claims**: Do not claim any universal model-specific prompt optimization beyond the locally tested task contract documented in [docs/ANTIGRAVITY_DELEGATION.md](docs/ANTIGRAVITY_DELEGATION.md).
